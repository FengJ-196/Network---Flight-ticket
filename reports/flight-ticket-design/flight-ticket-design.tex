% MAIN 07 | 1:30 | Sources: message-spec.md sections 1-2
\begin{frame}[fragile]{TCP framing and transport rules}
\small
\textbf{One message:} one UTF-8 JSON object followed by LF.
\begin{lstlisting}
{"v":1,"type":"PING","id":"p1","data":{}}\n
\end{lstlisting}
\begin{tabularx}{\textwidth}{@{}lY@{}}
\toprule
\textbf{Condition} & \textbf{Required receiver/sender behavior}\\
\midrule
Partial read & Keep bytes until LF completes the frame\\
Several frames in one read & Process complete lines in order, retain the unfinished suffix\\
Partial write & Continue until the entire frame and LF have been sent\\
Frame limit & At most 65,536 payload bytes, excluding LF and optional CR\\
Timing & Incomplete frame: 10 s. Idle receive: 300 s. Client request: 10 s\\
\bottomrule
\end{tabularx}
\gap
One client request may wait at a time. Serialize complete outgoing frames.
\end{frame}
\note{TCP supplies an ordered byte stream, not message boundaries. The displayed backslash-n illustrates the final LF byte. CRLF is tolerated. Decode strict UTF-8 after receiving a complete bounded line. An oversized frame closes that connection. Client PING every 60 seconds keeps an idle connection active.}

% MAIN 08 | 1:30 | Sources: message-spec.md envelope
\begin{frame}[fragile]{Request, response and push envelopes}
\small
\lead{Request and matching response}
\begin{lstlisting}
{"v":1,"type":"PING","id":"p1","data":{}}
{"v":1,"type":"PING_RESP","id":"p1","ok":true,
 "code":"OK","data":{"serverTime":"2026-11-04T10:00:00+07:00"}}
\end{lstlisting}
\lead{Failure reply}
\begin{lstlisting}
{"v":1,"type":"LOGIN_RESP","id":"l1","ok":false,
 "code":"E_BAD_CREDENTIALS","message":"Invalid credentials","data":{}}
\end{lstlisting}
\begin{points}
\item \msg{v}: protocol version. \msg{type}: operation. \msg{id}: request correlation.
\item \msg{NOTIFY} uses \msg{id:null} and has no \msg{ok} field.
\item Clients dispatch by type/ID. A push does not complete a pending request.
\end{points}
\end{frame}
\note{These are complete illustrative PING and login-failure frames. Error text is for people, while code drives client behavior. Responses echo the request ID and append _RESP to the request type. Unknown request fields are rejected. Clients ignore unknown response fields for compatible additions. A full push example is in the appendix.}

\begin{frame}{Message processing on both ends}
\small
\begin{columns}[T]
\column{0.49\textwidth}
\lead{Server processing}
\begin{enumerate}\setlength{\itemsep}{5pt}
\item Assemble and parse a bounded frame.
\item Log safely. Validate envelope, fields, role and ownership.
\item Check replay and business guards.
\item Commit inventory, balance, booking and saved result together.
\item Enqueue reply/push and write all bytes.
\end{enumerate}
\column{0.47\textwidth}
\lead{Client processing}
\begin{enumerate}\setlength{\itemsep}{5pt}
\item Validate input and retain request ID/key.
\item Send one request and keep receiving.
\item Dispatch NOTIFY separately from replies.
\item Match response ID/type and show authoritative results/errors.
\item On timeout, reconnect, log in and reconcile.
\end{enumerate}
\end{columns}
\gap
One domain lock plus a SQL transaction serializes small-demo mutations. Socket writes and provider calls happen after release.
\end{frame}
\note{Explain both ends, as the lecture requires message processing rather than just an opcode list. A domain mutation either commits all effects or rolls back. The single-lock design is a proposed simple choice for this course dataset. It avoids two customers acquiring the last seat and prevents conflicting payment/admin changes.}

\small
\begin{tabularx}{\textwidth}{@{}lY@{}}
\toprule
\textbf{Failure class} & \textbf{Response and recovery}\\
\midrule
Invalid complete JSON frame & ERROR\_RESP / E\_BAD\_JSON. Keep the connection usable\\

Business rejection & Typed error, such as E\_SEATS\_UNAVAILABLE or E\_INSUFFICIENT\_BALANCE\\

\item Distinguish SEND\_ATTEMPT, SEND\_SUCCESS and SEND\_FAILURE.
\item Redact passwords, contacts and passenger identity data. Never log malformed raw payloads.
\end{points}
\end{frame}

\begin{frame}{Recovery after a lost reply}
\small
\textbf{Example:} payment commits, but the connection closes before the reply arrives.
\gap
\begin{enumerate}\setlength{\itemsep}{7pt}
\item Client records an unknown outcome and keeps the original payload/key.
\item Reconnect and log in again with a fresh connection request ID.
\item Retry the same mutation with its original idempotencyKey.
\item Server returns the saved success before checking the current booking state.
\item Client refreshes the booking, balance and unread notifications.
\end{enumerate}
\gap
\begin{tabularx}{\textwidth}{@{}lY@{}}
\toprule
Request ID & Correlates one exchange on one connection\\
Idempotency key & Identifies a committed operation across reconnect/restart\\
\bottomrule
\end{tabularx}
\end{frame}
\note{The key scope is user, operation type and key. The server stores normalized payload and result in the mutation transaction. Same key with another payload yields E_IDEMPOTENCY_CONFLICT. BOOK, PAY, CANCEL, CHANGE and ADMIN_UPDATE use durable keys. Read-only calls can simply repeat. This guarantee does not promise exactly-once email delivery.}
